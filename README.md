# latency-lab

A mini test bench to **see** p50 / p95 / p99, histograms and buckets in action, not just read about them.

```
k6 (load) ──► app (Node.js + prom-client + OpenTelemetry) ──HTTP──► wallet (second service)
                   │ /metrics (scraped by Prometheus)  ──► Prometheus ──► Grafana (dashboard)
                   └ traces of both services (OTLP) ──► OTel Collector (tail sampling) ──► Jaeger
```

## Running

```bash
docker compose up --build
```

- Grafana (the dashboard opens right away, no login): http://localhost:3001
- Prometheus: http://localhost:9090
- Jaeger (traces): http://localhost:16686
- Raw service metrics: http://localhost:3000/metrics

Load is generated by the `k6` container (~40 requests/s, 15 minutes). To stop it: `docker compose stop k6`.
Wait 1–2 minutes for data to accumulate on the charts.

## What to look at on the dashboard

| What happens | Where it shows |
|---|---|
| `/fast` responds in 5–15 ms | p50 is low and flat |
| `/tail`: 2% of requests take 500–900 ms | p99 is high, p50 does not change; the mean barely moves |
| From minute 3 to minute 6 k6 calls `/blocking` every second (blocks the event loop for 200 ms) | p95/p99 grow for **all** routes, and so does event loop lag, although `/fast` itself did not change |
| Bucket heatmap | shows which buckets the requests fall into |

Main takeaway: **p50 can be fine while p99 is already bad**, and the mean hides it (the "Mean vs p99" panel).

## Where to look at traces

- **Jaeger:** http://localhost:16686 → Service `latency-lab` → Find Traces. There is also a link at the top of the Grafana dashboard.
- **Grafana:** Explore → the `Jaeger` data source → Search. The same traces, but next to the metrics.
- Traces appear with a delay of about 10 seconds: the Collector waits 5 seconds for a trace to finish before deciding whether to keep it.
- Not all traces are stored: all those slower than 300 ms, all with errors, and 10% of the rest. There will be few fast ones, and that is normal.
- If Jaeger is empty: check `docker compose logs otel-collector` and `docker compose logs app`; make sure `OTEL_EXPORTER_OTLP_ENDPOINT` is set for `app`.

## Traces (OpenTelemetry)

Metrics tell you "where it hurts"; a trace shows **which part of a specific slow request** consumed the time.

1. Open Jaeger → Service `latency-lab` → Find Traces.
2. Set Min Duration to `500ms`. Only the slow `/tail` requests remain.
3. Open a trace. It has **two services**, and almost all the time is taken by the `db.query` span inside `wallet` (attribute `tail.slow=true`):

```
latency-lab: GET /tail
  └ latency-lab: request handler - /tail
      └ latency-lab: wallet.getBalance
          └ wallet: GET /balance
              └ wallet: request handler - /balance
                  └ wallet: db.query      ← the time was lost here
```

   Fast `/fast` requests have a `cache.lookup` span.

### How a trace crosses services

Before calling wallet, `app` puts the `traceparent` HTTP header (`00-<trace_id>-<span_id>-01`) on the request,
see `src/wallet-client.ts` (`propagation.inject`). The http auto-instrumentation in `wallet` reads this header
and makes its spans children of it. This way `trace_id` stays the same across both services.

### trace_id in logs

Logs are JSON; inside an active span they contain `trace_id` and `span_id` (`src/logger.ts`):

```bash
docker compose logs app wallet | grep <trace_id from Jaeger>
```

You will see lines from both services with the same `trace_id`.

The Collector does **tail sampling** (`otel/collector-config.yaml`): it keeps all traces slower than 300 ms, all with errors, and 10% of the rest.
That is why Jaeger has many slow traces and few fast ones. This is by design: storing everything is expensive.

How it is enabled: `src/tracing.ts` starts the SDK only if `OTEL_EXPORTER_OTLP_ENDPOINT` is set.
`src/tracing-init.ts` is imported first in `server.ts`, otherwise the http/express auto-instrumentation will not have time to hook in.
Custom sections are wrapped with `withSpan` from `src/spans.ts`. Without the SDK (for example, in tests) it is a no-op.

## Alerts

The rules are in `prometheus/alerts.yml`, status: http://localhost:9090/alerts (also the "Active alerts" table at the bottom of the dashboard).

| Alert | Condition | When it fires on the bench |
|---|---|---|
| `FastRouteP95High` | p95 of `/fast` > 100 ms, 30 s | minutes 3–6 (event loop blocking) |
| `EventLoopLagHigh` | event loop lag p99 > 100 ms, 30 s | same time |
| `ErrorRateHigh` | 5xx share > 5%, 1 min | after `docker compose stop wallet` |
| `TailRouteP99Degraded` | p99 of `/tail` > 1 s, 1 min | only if the tail gets worse than normal; silent otherwise |

States: `inactive` (all good) → `pending` (condition met, but not yet for longer than `for`) → `firing` (alarm).
The `for` field protects against false alarms on one-off spikes.

Prometheus only **evaluates** the rules. Sending to Slack or PagerDuty is Alertmanager's job; this bench does not have one.

Rule syntax check: `docker compose run --rm --entrypoint promtool prometheus check rules /etc/prometheus/alerts.yml`.

## How it works

- `src/metrics.ts` — the `http_request_duration_seconds` histogram and the middleware that measures request time.
  The `route` label is the route template, not the real URL: otherwise every unique URL creates a new series (cardinality explosion).
- `src/app.ts` — three endpoints and `/metrics`. Randomness and "sleep" are replaced in tests.
- `src/wallet.ts`, `src/wallet-client.ts`, `src/wallet-db.ts` — the second service, its client (with a timeout and context propagation) and a simulated DB.
- `src/percentile.ts` — a hand-written percentile (nearest-rank) to understand what it computes.
- The dashboard computes percentiles with the query:
  `histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[1m])))`.
  The value is approximate: accuracy depends on the bucket boundaries (`LATENCY_BUCKETS`).

## Tests (no Docker)

```bash
npm install
npm test
```

25 tests: percentiles (including "the tail is visible in p99 but not in the mean"), presence of the histogram and buckets in `/metrics`,
bucket cumulativity, grouping of unknown URLs into `unmatched`, `/tail` and `/blocking` behavior, spans (`withSpan`, errors, attributes in routes), `traceparent` propagation between services, `trace_id` in logs, and behavior when wallet is down (502, not a hang).

## Try it yourself (good exercises before an interview)

1. Remove the buckets around `0.1` from `LATENCY_BUCKETS` and see how p99 "jumps".
2. Add a timeout and a circuit breaker for the slow branch of `/tail`.
3. Move the heavy code from `/blocking` into `worker_threads` and compare event loop lag.
4. Add a Prometheus alert: `p99 > 0.5 s` for longer than 2 minutes.
5. In `collector-config.yaml` change the `threshold_ms` threshold and the `sampling_percentage` share and see how the set of traces in Jaeger changes.
6. Stop wallet (`docker compose stop wallet`): `/tail` starts returning 502, and Jaeger shows traces with errors. Tail sampling keeps all of them.
7. Add metric scraping from wallet (`wallet:3000`) to Prometheus and build a per-service dashboard.
8. Draw on paper how you would look for the cause if p99 rose in production (metrics → traces → logs).

## For the interview: how to explain it

"I measure latency with a histogram: I pick the buckets to match the SLO, compute percentiles in Prometheus with `histogram_quantile`,
and look at p95 and p99, not the mean. If p99 rose but p50 did not, I look for a rare slow path: a DB query, retries, GC or event loop blocking."
